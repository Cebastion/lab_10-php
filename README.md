# Лабораторна робота № 10

**Тема:** Laravel. Консольні команди Artisan
**Проєкт:** REST API для системи управління завданнями (Task Tracker)

## Мета

Навчитися створювати власні Artisan-команди в Laravel, працювати з аргументами та опціями команд і виводити дані в консоль у зручному вигляді.

## Структура файлів

```
app/Console/Commands/
    GenerateTaskReport.php          (tasks:report)
    CreateTaskInteractive.php       (tasks:create-interactive)
```

Для роботи потрібні модель `Task`, `TaskObserver`, подія `TaskCreated` і слухач `NotifyAssignee` з попередньої лабораторної роботи.

## Хід роботи

### Крок 1. Команда tasks:report

Згенерував команду:

```
php artisan make:command GenerateTaskReport
```

Сигнатура команди:

```php
protected $signature = 'tasks:report {--project_id=}';
```

Логіка методу `handle()`:

1. Отримую значення опції через `$this->option('project_id')`.
2. Якщо опцію вказано, додаю до запиту фільтр `where('project_id', ...)`.
3. Якщо завдань немає, виводжу попередження через `warn()`.
4. Якщо завдання є, виводжу `info()` з їх кількістю та таблицю через `table()` з колонками ID, Назва, Статус, Дедлайн.

```php
$this->info("Знайдено завдань: {$tasks->count()}");

$this->table(
    ['ID', 'Назва', 'Статус', 'Дедлайн'],
    $tasks->map(fn (Task $task) => [
        $task->id,
        $task->title,
        $task->status,
        $task->due_date ? (string) $task->due_date : '—',
    ])->all()
);
```

Окрім того, додав дві невеликі перевірки: якщо `--project_id` не є числом, команда виводить помилку, а якщо проєкту з таким ID немає в базі, виводить окреме попередження.

### Крок 2. Команда tasks:create-interactive

Згенерував другу команду:

```
php artisan make:command CreateTaskInteractive
```

Сигнатура: `tasks:create-interactive`.

Діалог побудований так:

| Метод       | Що запитує                                                           |
| ----------- | -------------------------------------------------------------------- |
| `ask()`     | назву, опис, ID проєкту, дедлайн та ID виконавця                     |
| `choice()`  | статус із варіантів `new`, `in_progress`, `done`                     |
| `confirm()` | чи зберігати завдання                                                |

Що ще зробив у команді:

- Перед збереженням перевіряю введені дані через `Validator` з тими самими правилами, що й у `StoreTaskRequest`. Якщо є помилки, команда їх виводить і завершується.
- У таблиці `tasks` поле `author_id` обов'язкове, а в діалозі про автора не питають. Тому автором ставлю власника проєкту (`$project->user_id`).
- Перед питанням про підтвердження виводжу таблицю з введеними даними, щоб було видно, що саме буде збережено.
- Якщо користувач підтвердив, створюю завдання через `Task::create()` і виводжу `info()` з ID нового запису. Якщо відмовився, виводжу `warn()` про скасування.

```php
if (! $this->confirm('Зберегти завдання?', true)) {
    $this->warn('Створення завдання скасовано.');

    return self::SUCCESS;
}

$task = Task::create([...]);

TaskCreated::dispatch($task);

$this->info("Завдання успішно створено. ID: {$task->id}");
```

### Крок 3. Перевірка інтеграції з подіями

Запустив команду:

```
php artisan tasks:create-interactive
```

Приклад діалогу:

```
 Назва завдання:
 > Налаштувати CI

 Опис завдання (Enter — пропустити):
 > Додати збірку в GitHub Actions

 ID проєкту:
 > 1

 Дедлайн у форматі YYYY-MM-DD (Enter — пропустити):
 > 2026-12-15

 ID виконавця (Enter — пропустити):
 > 2

 Статус завдання:
  [0] new
  [1] in_progress
  [2] done
 > 0

 Зберегти завдання? (yes/no) [yes]:
 > yes

Завдання успішно створено. ID: 31
```

Після цього відкрив `storage/logs/laravel.log` і побачив записи:

```
[2026-11-24 12:00:01] local.INFO: TaskObserver: створено нове завдання {"task_id":31,"title":"Налаштувати CI"}
[2026-11-24 12:00:01] local.INFO: NotifyAssignee: сповіщення виконавця про нове завдання {"task_id":31,"task_title":"Налаштувати CI","assignee_id":2,"assignee_name":"Test User","message":"Завдання «Налаштувати CI» призначено користувачу Test User"}
```

**Висновок щодо Observer та події.** Ці дві речі поводяться з консоллю по-різному:

- `TaskObserver` працює автоматично. Він прив'язаний до моделі `Task`, тому реагує на `Task::create()` звідки б його не викликали: з контролера, з консолі чи з тінкера.
- `TaskCreated` автоматично **не** викликається. У ЛР9 цю подію запускав `TaskController` після збереження, а команда контролер не використовує. Тому в команді я викликаю `TaskCreated::dispatch($task)` вручну. Без цього рядка в лозі був би тільки запис від `TaskObserver`, а `NotifyAssignee` не спрацював би.

Якщо в консолі відповісти на підтвердження `no`, виводиться попередження про скасування, завдання в базі не з'являється і в лог нічого не пишеться.

### Крок 4. Тестування команди tasks:report

Перевірив три варіанти виклику.

**1. Без параметрів** — виводить усі завдання:

```
php artisan tasks:report
```

```
Знайдено завдань: 31
+----+--------------------------+-------------+---------------------+
| ID | Назва                    | Статус      | Дедлайн             |
+----+--------------------------+-------------+---------------------+
| 1  | Підготувати звіт         | new         | 2026-12-01 00:00:00 |
| 2  | Оновити документацію     | in_progress | —                   |
| .. | ...                      | ...         | ...                 |
+----+--------------------------+-------------+---------------------+
```

**2. З фільтром** — тільки завдання вказаного проєкту:

```
php artisan tasks:report --project_id=1
```

Виводиться така ж таблиця, але лише з завданнями, у яких `project_id = 1`.

**3. З неіснуючим ID проєкту:**

```
php artisan tasks:report --project_id=999
```

```
Проєкт з ID 999 не знайдено.
```

Якщо проєкт існує, але завдань у нього немає, виводиться попередження `Завдань не знайдено.`

Якщо передати не число (`--project_id=abc`), команда виведе помилку і завершиться з кодом `1`.

Перевірити, що команди зареєстровані, можна через `php artisan list tasks`. У Laravel 11/12 (як і в 10) команди з `app/Console/Commands` підхоплюються автоматично, тому окремо реєструвати їх не потрібно.

## Результат

У проєкті з'явились дві власні Artisan-команди: `tasks:report` для звіту по завданнях і `tasks:create-interactive` для створення завдання через діалог у консолі. Обидві перевірив. `TaskObserver` спрацьовує при створенні завдання з консолі автоматично, а подію `TaskCreated` (а разом з нею й слухача `NotifyAssignee`) довелось викликати вручну в самій команді.

## Висновки

У цій лабораторній роботі я навчився створювати власні Artisan-команди, працювати з опціями (`option()`), інтерактивним введенням (`ask()`, `choice()`, `confirm()`) та форматованим виводом (`info()`, `warn()`, `error()`, `table()`). Також зрозумів різницю між Observer і подією: Observer прив'язаний до самої моделі й працює в будь-якому місці застосунку, а подія спрацьовує лише там, де її явно викликали.
